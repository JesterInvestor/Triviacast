# Triviacast — Challenge Mode (Bots) Plan

Last updated: 2025-11-24

This document describes a comprehensive plan to add a social, asynchronous 1v1 "Challenge Mode" to the Triviacast mini app that uses bots to track and announce matches on Farcaster. It covers UX, cast templates, bot architecture (dev and production), storage schema, implementation steps, testing, deployment checklist, and optional features.

---

## Goals

- Provide an engaging, social 1v1 trivia challenge flow where users can: search friends, play a quiz, cast results tagging both players, and have a bot automatically detect matches and announce winners.
- Keep the flow simple and reliable: consistent cast format, unique challenge IDs, and robust bot parsing and deduplication.
- Support both quick development (polling + SQLite) and production readiness (webhooks, PostgreSQL/Redis, observability).

---

## High-level User Flow

1. User A opens Triviacast and searches for a friend (via Neynar user search API).
2. User A plays the quiz and finishes; the mini app shows a share button.
3. The app generates a standardized cast and posts it (tags User A & User B, includes score, hashtag, challenge link, and optional challenge ID).
4. Bot listens for challenge casts (#triviacastchallenge) and records the match.
5. User B clicks the link, plays the quiz, and posts their results using the same template.
6. Bot detects both results, compares scores, and replies (in-thread or on both casts) declaring the winner.

Optional: Bot may award points, update a leaderboard, or announce rematch links.

## Cast Templates & Parsing

Use a consistent, machine-friendly cast format. The mini app should auto-generate these casts via a Share/Challenge button.

Example challenger cast (generated by the app):

"This is the challenge cast @jesterinvestor @dwr — I just played Triviacast with 5 (🔥 5,500 T Points)! Think you can beat me? Take the Challenge on Triviacast — https://triviacast.xyz #triviacastchallenge-827A"

Responder cast should use the same pattern (same challenge ID):

"I accepted the Triviacast challenge from @jesterinvestor — I scored 6 (🔥 6,200 T Points)! #triviacastchallenge-827A https://triviacast.xyz"

Parsing recommendations:

- Detect hashtag: `#triviacastchallenge` (optionally with suffix `-<ID>`).
- Mentions: require at least two mentions in the challenger cast (challenger and opponent).
- Score: use a regex for numeric score and optional `T Points` token. Example regex (JS): `/([0-9]{1,3}(?:,[0-9]{3})?)\s*(?:T Points|TPoints|points)?/i`.
- Challenge ID: prefer `#triviacastchallenge-([A-Za-z0-9_-]{4,12})` to reliably match pairs in large volumes.
- Fallback pair key: if no challenge ID present, use sorted usernames (e.g., `alice-bob`) as a fallback match key; still encourage IDs for robustness.

Sample cast fields (recorded by bot):

- challenger_username
- opponent_username
- challenger_score
- opponent_score
- challenge_id (nullable)
- challenger_cast_hash
- opponent_cast_hash
- status (pending/complete/archived)
- created_at / finished_at

## Bot Architecture

Two phases: Prototype (fast to build) and Production (scalable and robust).

Prototype (Dev):

- Approach: Poll Neynar cast search endpoint every N seconds for new casts containing `#triviacastchallenge`.
- Storage: lightweight SQLite via `knex` or direct `sqlite3`. Keep an in-memory cache for dedup.
- Behavior: Parse casts, insert or update challenge rows, when both sides present mark `complete`, publish announcement cast via agent API.
- Pros: Fast to build, deploy locally or on small VM.
- Cons: Higher latency, less scalable, polling cost.

Production:

- Use webhooks (Neynar's webhook/agents API) to receive casts in real-time (preferred) or switch to efficient polling with watermarking.
- Storage: Postgres (preferred) or Redis (for ephemeral states) with a `challenges` table and `leaderboard` table.
- Idempotency: store cast hashes and transaction IDs; use DB constraints to avoid duplicate rows.
- Reliability: add retries, exponential backoff, and dead-letter queue for failed parsing.
- Observability: integrate Sentry for errors and Prometheus + Grafana for metrics. Add structured logs.
- Security: store agent API keys in environment variables / secrets manager, enforce minimal perms for agent, rotate keys.

Bot responsibilities:

- Detect challenge casts and parse metadata.
- Create or update a challenge record.
- When both results are present, compute winner and post a reply to both casts (or to the thread) with scores and a win/lose message.
- Optionally update a leaderboard, issue points, and respond to rematch requests.

## Database Schema (suggested)

Table: `challenges`

- `id` (serial primary key)
- `challenge_id` (string, unique if present)
- `pair_key` (string, fallback sorted usernames key)
- `challenger_username` (string)
- `challenger_score` (integer)
- `challenger_cast_hash` (string)
- `opponent_username` (string)
- `opponent_score` (integer)
- `opponent_cast_hash` (string)
- `status` (enum: pending, complete, canceled, archived)
- `created_at`, `updated_at`, `finished_at`

Table: `leaderboard` (optional)

- `id`, `username`, `total_points`, `wins`, `losses`, `last_played_at`

Indexes:

- index on `challenge_id`
- index on `pair_key`
- index on `status`

## Parsing & Matching Logic (pseudocode)

1. On new cast (webhook or poll): skip if author is bot.
2. If cast contains `#triviacastchallenge`, parse mentions and score.
3. Extract `challenge_id` if present; else compute `pair_key` = sort(mentions).
4. Query `challenges` by `challenge_id` or `pair_key`:
   - If no record: insert with challenger info and status `pending`.
   - If record exists and other player's result is missing: update record with opponent info and status `complete`.
   - If record exists and both present: ignore as duplicate or consider rematch logic.
5. When `complete`: compute winner and reply to both casts with a templated message.
